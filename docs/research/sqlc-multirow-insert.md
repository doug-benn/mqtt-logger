# Research: variable-length batch INSERT with sqlc + pgx v5

Context: the temperature batching effort pins a multi-row `INSERT` over pgx,
generated by sqlc (v1.31.1, the version this repo's checked-in code was generated
with — see `database/queries/rainfall.sql.go`). sqlc does not expand `$1, $2, ...`
placeholders into N rows, so a mechanism is needed for a variable-length batch.

All claims below were verified against primary sources: sqlc and pgx GitHub
repositories/official docs, the PostgreSQL manual, plus generation runs of the
pinned sqlc binary and runtime tests against this repo's own PostgreSQL 18
container (`docker-compose.yaml`, `postgres:18-alpine` on port 5435) using
pgx v5.11.0 (the version in `go.mod`).

## The mechanisms sqlc offers

### 1. Fixed-row multi-row VALUES — not variable length

A `VALUES ($1, $2), ($3, $4)` query generates one flat Go parameter per
placeholder (`Value`, `ReceivedAt`, `Value_2`, `ReceivedAt_2`). sqlc has no
feature that replicates a placeholder pattern N times at runtime; N is baked
into the SQL text. (Verified with sqlc v1.31.1 generation.)

### 2. Multi-argument `unnest` (ROWS FROM form) — broken in sqlc, works in Postgres

The idiomatic Postgres batch shape

```sql
-- name: CreateTemperatures :exec
INSERT INTO temperature (value, received_at)
SELECT * FROM unnest($1::float8[], $2::timestamptz[]);
```

is valid PostgreSQL — the manual documents `unnest(anyarray, anyarray[,...])`
as "Expands multiple arrays ... into a set of rows ... only allowed in a query's
FROM clause" (<https://www.postgresql.org/docs/current/functions-array.html>),
and the FROM-clause table-function rules cover the parallel-column ROWS FROM
semantics (<https://www.postgresql.org/docs/current/queries-table-expressions.html#QUERIES-TABLE-EXPRESSIONS>,
§7.2.1.4). But sqlc's analyzer rejects it:

```
sql/query.sql:4:6: function unnest(unknown, unknown) does not exist
```

(Reproduced with the official v1.31.1 release binary.) This is sqlc issue
[#3507 "UNNEST can't handle multiple arrays"](https://github.com/sqlc-dev/sqlc/issues/3507)
(open, labeled `bug`; the same failure was reported in 2021 in
[#958 "is unnest supported?"](https://github.com/sqlc-dev/sqlc/issues/958),
closed with the workaround below rather than a fix). A fix,
[PR #3738 "fix: Support multi-argument version of unnest"](https://github.com/sqlc-dev/sqlc/pull/3738),
has been open and unmerged since December 2024 (state: open, merged: false as of
this writing). It is not in v1.31.x — neither v1.31.0 nor v1.31.1 release notes
mention unnest (<https://github.com/sqlc-dev/sqlc/releases>).

### 3. Parallel single-argument `unnest` in the select list — works, and generates the right signature

The workaround from issue #958 (and the one the sqlc maintainers pointed to when
closing it) is to call `unnest` once per column in the SELECT list:

```sql
-- name: CreateTemperatures :exec
INSERT INTO temperature (value, received_at)
SELECT unnest(@values::float8[]), unnest(@received_at::timestamptz[]);
```

Multiple set-returning functions in the same SELECT list are evaluated in
lockstep: column *i* of row *r* comes from element *r* of array *i*, and shorter
arrays are NULL-padded to the longest (the same padding rule the manual states
for the ROWS FROM form, §7.2.1.4 above; verified live against this repo's
PostgreSQL 18 — see "Runtime behavior" below). This form also passes sqlc's
analyzer because each `unnest` call is single-argument.

sqlc v1.31.1 generates (verified with the official release binary, using the
repo's `sqlc.yaml` settings — `sql_package: pgx/v5` and the `timestamptz ->
time.Time` override):

```go
const createTemperatures = `-- name: CreateTemperatures :exec
INSERT INTO temperature (value, received_at)
SELECT unnest($1::float8[]), unnest($2::timestamptz[])
`

type CreateTemperaturesParams struct {
	Values     []float64
	ReceivedAt []time.Time
}

func (q *Queries) CreateTemperatures(ctx context.Context, arg CreateTemperaturesParams) error {
	_, err := q.db.Exec(ctx, createTemperatures, arg.Values, arg.ReceivedAt)
	return err
}
```

Notes on the generated code:

- The `@values`/`@received_at` named parameters (sqlc "Naming parameters",
  <https://docs.sqlc.dev/en/latest/howto/named-parameters.html>) become `$1`/`$2`
  in the emitted SQL and give the struct fields their names; without them sqlc
  emits `Column1`/`Column2`.
- Type mapping: `float8[]` -> `[]float64`, and `timestamptz[]` -> `[]time.Time`
  *because this repo's `sqlc.yaml` overrides `timestamptz` to `time.Time`*. The
  override applies to array parameters too. Without it, pgx/v5's default mapping
  wins and sqlc generates `[]pgtype.Timestamptz` (verified by generating with and
  without the override). pgx natively converts PostgreSQL arrays to Go slices of
  integers, floats, and strings (<https://github.com/jackc/pgx#features>), and
  `time.Time`/`[]time.Time` map to `timestamptz`/`timestamptz[]`.
- `:exec` returns only `error`; no `RETURNING`, no row count. Use `:execrows` if
  the affected-row count is wanted
  (<https://docs.sqlc.dev/en/latest/reference/query-annotations.html>).
- Empty slices: `[]float64{}` / `[]time.Time{}` insert zero rows without error
  (verified live). The caller should skip the flush on an empty batch anyway.

### Runtime behavior (verified against PostgreSQL 18 + pgx v5.11.0)

Run against this repo's own stack with the exact generated SQL above:

- Equal-length arrays: `INSERT 0 2`; element *i* of each array lands in row *i*,
  timestamps preserved exactly.
- Mismatched lengths: the shorter array is NULL-extended; with a `NOT NULL`
  column this fails with `SQLSTATE 23502` rather than silently misaligning —
  the batch builder must keep the arrays the same length.
- NULL elements: `[]float64` cannot express a NULL element; `[]*float64` works
  and pgx sends the nil element as SQL NULL (verified: server rejected it on the
  `NOT NULL` column). Not needed here — both temperature columns are `NOT NULL` —
  but worth knowing if nullable columns ever ride an unnest batch. sqlc generates
  plain `[]float64`, so a nullable variant would need a type override.
- Statement caching: pgx v5's default `QueryExecMode` is
  `QueryExecModeCacheStatement`, which prepares a statement on first use, caches
  it in a per-connection LRU (default capacity 512, keyed by SQL text), and
  executes in a single round trip thereafter
  (<https://github.com/jackc/pgx/blob/v5.11.0/conn.go>, `QueryExecMode`
  constants and `ParseConfig` docs). Because the batch size is *in the arguments*
  (array lengths), not the SQL text, the unnest query has one SQL string
  regardless of batch size: one prepare per connection, then one round trip per
  flush. Repeated executions verified live. (A pgxpool changes nothing here — it
  hands out `pgx.Conn`s with the same defaults, per the sqlc pgx guide
  <https://docs.sqlc.dev/en/latest/guides/using-go-and-pgx.html>.)

### 4. `:batchexec` (pgx Batch pipelining) — excluded by prior decision, documented for the record

```sql
-- name: CreateTemperature :batchexec
INSERT INTO temperature (value, received_at) VALUES ($1, $2);
```

generates `CreateTemperature(ctx, arg []CreateTemperatureParams) *CreateTemperatureBatchResults`,
which queues one per-row statement into a `pgx.Batch` and sends it via
`SendBatch` (<https://docs.sqlc.dev/en/latest/reference/query-annotations.html>;
code verified by generation). pgx sends the queued statements as one pipelined
message stream on the extended protocol (v5.11.0 `conn.go` `SendBatch`). The
decision so far rules this out (single multi-row INSERT preferred), so it is not
the recommendation; note it requires iterating `BatchResults.Exec` per row and
per-row errors surface through the callback.

### 5. `:copyfrom` (COPY protocol) — excluded by prior decision, documented for the record

```sql
-- name: CreateTemperature :copyfrom
INSERT INTO temperature (value, received_at) VALUES ($1, $2);
```

generates a `pgx.CopyFromSource` iterator and a method taking
`[]CreateTemperatureParams` that calls `db.CopyFrom(...)`
(<https://docs.sqlc.dev/en/latest/reference/query-annotations.html> and
<https://docs.sqlc.dev/en/latest/howto/insert.html>; code verified by
generation). sqlc's own docs describe it as "insert rows a lot faster than
sequential inserts". It is excluded from this effort by the pinned decision
(multi-row INSERT, not COPY), but it is the fastest option in the measurements
below.

There is no other sqlc feature for variable-length inserts: no "insert many"
expansion, and `sqlc.slice()` only expands `IN (...)` placeholder lists, not
`VALUES` rows
(<https://docs.sqlc.dev/en/latest/howto/select.html>). Hand-written query text
with a sqlc-generated DBTX stub was considered unnecessary given option 3.

## Performance (indicative, this machine, PostgreSQL 18, pgx v5.11.0)

20,000 rows inserted through the repo's own Postgres container, statement caches
warm, single connection:

| mechanism                                   | time for 20k rows |
|---------------------------------------------|-------------------|
| per-row `Exec` in one transaction           | ~400 ms           |
| pgx `Batch` of per-row statements (batchexec shape) | ~70–86 ms  |
| unnest, whole slice in one exec             | ~30–55 ms         |
| unnest, chunked execs (500 rows) in one tx  | ~29–32 ms         |
| `CopyFrom`                                  | ~22 ms            |

These are single-run local numbers, not a benchmark suite; treat them as
ordering, not precision. The ordering matches the PostgreSQL manual's guidance in
"Populating a Database" (<https://www.postgresql.org/docs/current/populate.html>):
`COPY` "is almost always faster than using INSERT, even if PREPARE is used and
multiple insertions are batched into a single transaction", and batching
insertions into one transaction avoids per-row commit work. The unnest batch is
within ~1.4x of `CopyFrom` here and ~10x faster than per-row inserts — consistent
with it being one round trip of one statement instead of N statements or N
round trips.

## Recommendation

Use the **`:exec` unnest-over-typed-arrays query with parallel single-argument
`unnest` calls in the SELECT list** (mechanism 3):

```sql
-- name: CreateTemperatures :exec
INSERT INTO temperature (value, received_at)
SELECT unnest(@values::float8[]), unnest(@received_at::timestamptz[]);
```

It is the only mechanism that satisfies every pin of the ticket: variable-length
batch, one multi-row INSERT statement (not COPY, not pgx batch pipelining),
fully generated by the repo's pinned sqlc v1.31.1, typed end to end (the repo's
existing `timestamptz -> time.Time` override extends to the array parameter, so
`[]float64` / `[]time.Time` line up with `model.Temperature`), one prepared
statement per connection with one round trip per flush under pgx's default
statement cache, and empirically ~10x per-row inserts while staying close to
COPY. The literal `SELECT * FROM unnest($1, $2)` spelling is nicer SQL but is
blocked by the open sqlc analyzer bug (#3507); do not hold the implementation
hostage to PR #3738 — when it merges, the spelling can be swapped with no
generated-signature change.

Ticket 02 implementation notes:

- Guard the flush: skip the exec on an empty batch (harmless but pointless).
- Keep `values` and `received_at` the same length; unequal lengths fail with a
  23502 on the NOT NULL column rather than misaligning, but that is a programming
  error the repo should assert, not surface from Postgres.

## Tradeoffs

- **vs. fixed-row multi-row VALUES** (`VALUES ($1,$2),($3,$4),...`): unnest keeps
  one SQL string and a stable statement-cache entry for any batch size; fixed-N
  needs a family of generated queries per N and flat per-placeholder parameters.
- **vs. `:batchexec`**: unnest is one statement and one round trip and was faster
  here (~30 ms vs ~70–86 ms for 20k rows); batchexec queues N single-row
  statements and surfaces errors through a per-row callback. batchexec was
  excluded by decision anyway.
- **vs. `:copyfrom`**: COPY remains the raw fastest (~22 ms) and is the manual's
  recommended bulk path, but it is excluded by decision and its generated method
  bypasses the normal query layer (protocol-level COPY, no SQL round trips to
  reason about).
- **vs. hand-written query with sqlc stubs**: would allow the multi-arg `unnest`
  spelling today, but adds a non-generated query file to maintain for no
  signature benefit over mechanism 3.
- **NULL elements**: plain `[]float64` cannot carry NULLs; nullable batch columns
  would need `[]*float64` plus a sqlc type override. Current schema is all
  `NOT NULL`, so this does not apply yet.
- **Lockstep semantics**: if the two arrays ever differ in length, Postgres
  NULL-pads the shorter one; the failure mode on NOT NULL columns is a loud 23502,
  but only when lengths actually diverge.
- **sqlc version caveat**: the workaround depends on sqlc accepting parallel
  single-arg `unnest` calls in the select list — it has (issues #958/#3507
  discussions span 2021–2026 and the form generates under v1.31.1, the latest
  release as of this writing). If a future sqlc release merges PR #3738, the
  `SELECT * FROM unnest($1, $2)` spelling becomes available; until then v1.31.x
  requires the parallel spelling.
